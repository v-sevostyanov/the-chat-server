# src

## Назначение

`src` содержит весь production-код backend-сервиса TheChat.
Структура выдержана в стиле **modular monolith**: инфраструктура и доменные модули разделены, а контракты между ними сделаны явными.

## Карта слоёв

- `app/` — сборка Fastify-приложения, загрузка конфигурации, entrypoint процесса.
- `plugins/` — инфраструктурные плагины Fastify (DB, Redis, auth, WebSocket, docs, errors и т.д.).
- `modules/` — доменные модули (`auth`, `users`, `chats`, `messages`, `presence`, `health`).
- `db/` — схема Drizzle, SQL-миграции, клиент БД.
- `shared/` — общие ошибки, схемы ответов, низкоуровневые helpers.

## Ключевые потоки

### HTTP-запрос

1. `app/buildApp` регистрирует плагины и модули.
2. Route в `modules/*/*.routes.ts` валидирует вход через TypeBox-схемы.
3. Handler делегирует в `service`.
4. Service использует repository.
5. Repository работает с PostgreSQL через Drizzle.
6. Ответ сериализуется в `data`/`error` envelope.

### Realtime (WebSocket)

1. `plugins/websocket` аутентифицирует соединение access token-ом.
2. События клиента валидируются Zod-схемами (`contracts.ts`).
3. `event-router` вызывает адаптеры домена (`presence`, `chats`).
4. Публикации fan-out идут через Redis Pub/Sub + `realtime-delivery`.
5. Соединения и подписки индексируются в памяти (`connection-index`).

## Архитектурные ограничения

- Route handlers должны быть тонкими; бизнес-логика только в `service`.
- Репозитории не должны знать о Fastify/HTTP.
- `shared/` не должен зависеть от доменных модулей.
- Real-time контракты должны оставаться явными и версионируемыми.
- Новые cross-module связи вводятся только через интерфейсы/адаптеры, а не прямые импорты случайных файлов.

## Как читать код новым участникам

1. Начать с `app/app.ts` (сборка приложения и порядок регистрации).
2. Перейти в `modules/index.ts` (какие домены включены).
3. В интересующем модуле читать в порядке: `routes -> handlers -> service -> repository`.
4. Для realtime-анализа дополнительно изучить `plugins/websocket/*`.
5. Для данных и ограничений проверить `db/schema/*` и `db/migrations/*`.

## Практика изменений

- Если меняется API-контракт, синхронно обновлять `*.schemas.ts` и OpenAPI-описание route.
- Если меняется поведение realtime, сверять HTTP fallback-сценарии (resync после reconnect).
- Если добавляется таблица/поле, отражать это в `db/schema` и миграциях.
- Документацию в поддиректориях обновлять вместе с кодом, чтобы аналитика и разработка оставались синхронизированными.
