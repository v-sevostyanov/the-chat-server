# AGENTS.md

## Идентичность проекта

Этот репозиторий содержит backend для **TheChat** — приложения для чата в реальном времени.

Технические предположения:
- Node.js
- TypeScript
- Fastify
- модульный монолит
- HTTP API + WebSocket
- PostgreSQL
- Redis

Это долгоживущая кодовая база. Оптимизируйте под:
- корректность
- сопровождаемость
- явную архитектуру
- низкую связанность
- предсказуемое поведение в сценариях реального времени и нестабильной сети

---

## Как работать в этом репозитории

Перед внесением изменений:

1. Разберитесь в локальном контексте.
2. Проверьте границы релевантных модулей.
3. Прочитайте `architecture.md` перед нетривиальными архитектурными изменениями.
4. Прочитайте `testing.md` перед завершением любой нетривиальной задачи.

Для нетривиальных задач предпочитайте:
1. анализ
2. небольшой шаг реализации
3. самопроверку
4. валидацию
5. итоговое объяснение

Не начинайте широкие переписывания кода, не проверив сначала структуру репозитория.

## Ожидания по архитектуре backend

Backend должен следовать стилю **модульного монолита**.

Ожидаемая верхнеуровневая структура:

- `src/app` — bootstrap и композиция сервера
- `src/plugins` — инфраструктурные плагины Fastify
- `src/modules` — доменные модули
- `src/db` — PostgreSQL-клиент, Drizzle-схема и SQL-миграции
- `src/shared` — общие типы, константы, helpers, utilities

Типичные доменные модули:
- auth
- users
- chats
- messages
- presence
- notifications
- files

Предпочитайте явные границы модулей.
Не создавайте огромный всезнающий сервис или один огромный файл роутов.

---

## Правила, специфичные для Fastify

- Уважайте инкапсуляцию Fastify и границы плагинов.
- По возможности регистрируйте функциональность через изолированные плагины/модули.
- Держите route handlers тонкими.
- Не размещайте бизнес-логику в route handlers.
- Не размещайте repository/data-access логику в route handlers.
- Избегайте скрытого поведения в hooks и decorators.
- Предпочитайте явные схемы и типизированные контракты для request/response payloads.
- Избегайте глобального изменяемого состояния.

---

## Правила real-time

Это backend для чата. Поведение в реальном времени является первоклассной частью системы.

Будьте внимательны к:
- порядку сообщений
- дублирующей доставке
- optimistic client flows
- поведению при reconnect
- статусу доставки
- состоянию прочтения
- состоянию typing
- состоянию presence

Не упрощайте real-time flows так, чтобы это блокировало будущую productionization.

Предпочитайте явные event contracts вместо ad hoc форм payload.

---

## Правила рефакторинга

Рефакторьте только когда:
- это требуется для корректного решения задачи
- текущая структура блокирует корректную реализацию
- рефакторинг явно снижает сложность

При рефакторинге:
- сохраняйте поведение, если задача не требует изменений поведения
- держите публичные контракты стабильными, если не указано иное
- не смешивайте широкие переписывания с небольшими feature-задачами без необходимости
- объясняйте причину в итоговом ответе

## Правила валидации

Перед завершением задачи:

1. Критически проверьте diff.
2. Запустите наиболее релевантные доступные проверки.
3. Исправьте очевидные проблемы, внесенные вашими изменениями.
4. Четко укажите, что было проверено, а что нет.

Предпочтительный порядок валидации:
1. targeted tests
2. typecheck
3. lint
4. build
5. более широкий test suite, когда релевантно

Никогда не заявляйте о валидации, которая фактически не запускалась.

Если скрипты репозитория отличаются от ожиданий, проверьте `package.json` и используйте реальные скрипты вместо вымышленных команд.

## Checklist для code review

Перед финализацией проверьте:

- смешанные ответственности
- архитектурный drift
- скрытую связанность
- дублированную логику
- слабую типизацию
- хрупкие conditionals
- сломанную обработку ошибок
- сломанные real-time assumptions
- сломанные auth assumptions
- сломанные validation assumptions
- dead code
- неясные имена

Если найдете проблему, внесенную собственным изменением, исправьте ее перед завершением.

## Ожидания по безопасности и надежности

Считайте backend программой, принимающей недоверенный ввод.

Всегда думайте о:
- validation
- authentication and authorization
- rate limiting surfaces
- ограничениях размера ввода
- утечке ошибок
- idempotency, где релевантно
- безопасности retry/reconnect
- безопасной обработке файлов
- безопасной обработке событий

Не добавляйте небезопасные shortcut ради удобства.

---

## Ожидания по итоговому ответу

Для изменений кода, конфигурации, схемы, миграций или документации в итоговом ответе:
- перечислите измененные файлы
- объясните, что изменилось
- объясните, почему этот подход соответствует репозиторию
- укажите выполненную валидацию
- укажите риски, ограничения или follow-up items, если релевантно

Для audit/report-only задач без изменений файлов:
- укажите проверенный scope
- кратко изложите конкретные findings и recommendations
- явно скажите, что файлы не изменялись
- укажите любую выполненную валидацию или cross-checking

Будьте конкретны.
Не давайте расплывчатых заявлений об успехе.
Не скрывайте tradeoffs.

## Запрещенные shortcut

- Не обходите архитектурные проблемы hacks.
- Не дублируйте логику ради скорости.
- Не оставляйте placeholder code как production-ready.
- Не меняйте несвязанное поведение молча.
- Не обходите validation, auth или error handling patterns без причины.
- Не создавайте огромные файлы, смешивающие transport, business logic и persistence concerns.

---

## Приоритет принятия решений

Когда появляются tradeoffs, расставляйте приоритеты в таком порядке:
1. корректность
2. целостность архитектуры
3. сопровождаемость
4. ясность
5. согласованность с репозиторием
6. скорость реализации

## Для сложных задач

Если задача большая, неоднозначная или рискованная:
- сначала предложите короткий план
- разделите работу на ясные шаги
- реализуйте инкрементально
- валидируйте каждый значимый шаг, когда это практично

Не начинайте большой рискованный rewrite без плана.
