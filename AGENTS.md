# AGENTS.md

## Идентичность проекта

Этот репозиторий содержит backend для **TheChat** - приложения для чата в реальном времени.

Технический стек: Node.js, TypeScript, Fastify, модульный монолит, HTTP API + WebSocket, PostgreSQL, Redis.

Оптимизируйте под корректность, сопровождаемость, явные границы, низкую связанность и предсказуемое поведение при real-time/reconnect сценариях.

## Как работать

- Сначала разберитесь в локальном контексте и границах затронутого модуля.
- Для нетривиальных архитектурных изменений прочитайте `architecture.md`.
- Для нетривиальных задач перед завершением прочитайте `testing.md`.
- Делайте небольшие изменения с высокой уверенностью.
- Не выполняйте несвязанные чистки, переименования публичных API/файлов/модулей или широкий rewrite без явной причины.
- Следуйте локальным паттернам, если они не вредят архитектуре или корректности.
- Если есть tradeoff, выбирайте: корректность, архитектура, сопровождаемость, ясность, согласованность, скорость.

## Язык

- Документация, Markdown, архитектурные заметки и внутренние инструкции пишутся на русском языке.
- Комментарии в коде пишутся на русском языке.
- Публичные API, идентификаторы, payload fields, протоколы и названия библиотек не переводятся.
- Английский допустим для внешних контрактов, API/errors и интеграций.

## Архитектура

Backend следует стилю модульного монолита.

- `src/app` - bootstrap, env/config, сборка Fastify, порядок регистрации, lifecycle.
- `src/plugins` - инфраструктурные Fastify-плагины и decorators.
- `src/modules` - доменные модули.
- `src/db` - PostgreSQL-клиент, Drizzle schema и SQL-миграции.
- `src/shared` - общие типы, ошибки, схемы и helpers без зависимости от доменов.

Код кладите в ближайший корректный слой:

- доменный use-case - `src/modules/<domain>`;
- инфраструктурный capability - `src/plugins/<name>`;
- новая таблица или миграция - `src/db/schema` + `src/db/migrations`;
- общий cross-module примитив - `src/shared`, только если он реально нужен нескольким модулям.

Не создавайте всезнающий сервис, огромный routes-файл или скрытую связность между модулями. Cross-module взаимодействие делайте через явные adapter/contract точки.

## Fastify и слои

- Уважайте инкапсуляцию Fastify и границы плагинов.
- Route handlers должны быть тонкими.
- Бизнес-логику и repository/data-access не размещайте в handlers.
- Плагины не должны импортировать доменные `service/repository`.
- Новый decorator объявляйте в `src/app/fastify.d.ts`.
- Предпочитайте явные request/response schemas и типизированные контракты.
- Избегайте глобального изменяемого состояния и скрытого поведения в hooks/decorators.

## Real-time

Real-time поведение является первоклассной частью системы. При изменениях учитывайте:

- порядок сообщений;
- дублирующую доставку;
- optimistic client flows;
- reconnect/retry;
- delivery/read/typing/presence состояния;
- явные event contracts вместо ad hoc payload.

Не упрощайте real-time flows так, чтобы это блокировало будущую productionization.

## Безопасность и надежность

Считайте входные данные недоверенными.

- Всегда думайте о validation, auth/authz, rate limiting surfaces и input size limits.
- Не допускайте утечек stacktrace, secrets и driver-specific internals.
- Учитывайте idempotency, retry/reconnect safety и безопасную обработку events/files.
- Не обходите validation, auth или error handling patterns ради удобства.

## Рефакторинг

Рефакторьте только когда это нужно для корректного решения, текущая структура блокирует реализацию или изменение явно снижает сложность. Сохраняйте публичные контракты и поведение, если задача не требует обратного.

## Валидация

Перед завершением:

1. Критически проверьте diff.
2. Запустите наиболее релевантные проверки.
3. Исправьте очевидные проблемы, внесенные вашими изменениями.
4. Четко укажите, что проверено, а что нет.

Предпочтительный порядок: targeted tests, typecheck, lint, build, более широкий test suite при необходимости. Используйте реальные scripts из `package.json`, не вымышленные команды.

## Итоговый ответ

Для изменений кода, конфигурации, схем, миграций или документации укажите:

- измененные файлы;
- что изменилось;
- почему подход соответствует репозиторию;
- выполненную валидацию;
- риски, ограничения или follow-up items.

Для audit/report-only задач явно скажите, что файлы не изменялись.

## Commit messages

Все предлагаемые и создаваемые commit messages должны соответствовать Conventional Commits и `commitlint.config.cjs`.

Формат:

```text
<type>(<scope>): <description>
```

Правила: lowercase `type`, краткий imperative-style `description` без точки, `scope` когда помогает, breaking changes через `!` и body/footer. Перед commit при возможности проверяйте сообщение через `npm run commitlint`.

Типичные `type`: `feat`, `fix`, `test`, `docs`, `refactor`, `chore`, `ci`, `build`.
