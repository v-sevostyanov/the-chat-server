# testing.md

## Назначение

Этот документ определяет, как нужно валидировать изменения в backend TheChat.

Тестирование здесь отвечает не только за корректность в идеальных условиях.
Оно также должно защищать:
- целостность архитектуры;
- поведение auth;
- realtime-поведение;
- обработку ошибок;
- граничные условия.

---

## Философия тестирования

Предпочитайте:
- узкие и содержательные тесты;
- детерминированную валидацию;
- тесты рядом с измененным поведением;
- явные assertions вместо широкой и расплывчатой coverage.

Не делайте:
- шумные тесты, которые проверяют детали реализации;
- пропуск валидации для нетривиального поведения;
- заявления об уверенности без проверок.

---

## Порядок валидации

Для нетривиальных изменений предпочитайте такой порядок:

1. точечные автоматизированные тесты для затронутого поведения
2. проверка типов
3. линтинг
4. проверка сборки
5. более широкие релевантные suites, если область влияния шире
6. ручная проверка для flows, которые сложно быстро покрыть автоматически

Если какие-то шаги нельзя выполнить, скажите об этом явно.

---

## Правило обнаружения scripts

Всегда сначала проверяйте реальные scripts репозитория.

Используйте команды, которые действительно существуют в `package.json`.
Не предполагайте названия команд.

Типичные примеры могут включать:
- `pnpm test`
- `pnpm test:unit`
- `pnpm test:integration`
- `pnpm test:e2e`
- `pnpm lint`
- `pnpm typecheck`
- `pnpm build`

Но реальный репозиторий является источником истины.

---

## Что обычно нужно тестировать

### При изменении route handlers или HTTP API

Проверьте:
- успешный сценарий;
- путь ошибки валидации;
- auth/permission path, если релевантно;
- маппинг ошибок;
- стабильность формы ответа.

### При изменении business logic/services

Проверьте:
- основные business rules;
- граничные случаи;
- условия отказа;
- idempotency, если релевантно;
- отсутствие случайной связности с transport layer.

### При изменении repositories/data access

Проверьте:
- корректность запросов;
- порядок;
- фильтрацию;
- pagination/cursor behavior;
- persistence edge cases;
- обработку null/empty результата.

### При изменении auth

Проверьте:
- authenticated path;
- unauthenticated path;
- unauthorized path;
- граничные случаи токенов/сессий;
- отсутствие случайного privilege escalation.

### При изменении websocket/realtime logic

Проверьте:
- форму event contract;
- preconditions подписки/соединения;
- устойчивость к дублирующимся событиям, где релевантно;
- reconnect-safe behavior, где практично;
- корректность state transitions;
- корректность message/event routing.

### При изменении files/uploads

Проверьте:
- разрешенный input path;
- отклоненный input path;
- валидацию размера/типа/metadata;
- authorization path;
- cleanup/error behavior, где релевантно.

---

## Типы тестов

### Модульные тесты

Используйте для:
- чистой business logic;
- validators;
- mappers;
- небольших services с mocked dependencies;
- utility functions.

Модульные тесты должны быть быстрыми и детерминированными.

### Интеграционные тесты

Используйте для:
- взаимодействия route + service + repository;
- database-backed behavior;
- auth-protected route flows;
- websocket event handling с реальной app wiring, где практично;
- интеграции plugins/modules.

Предпочитайте integration tests для backend-поведения, которое проходит через несколько layers.

### End-to-end тесты

Используйте экономно для:
- критичных user journeys;
- chat creation/send/read flows;
- auth + messaging flows;
- критичного пути file upload.

Не переносите всю уверенность в E2E.
Используйте их для high-value flows, а не как замену хорошим lower-level tests.

---

## Рекомендации по тестированию realtime

Realtime flows рискованны.
Когда меняется websocket или event logic, думайте через event contracts и state transitions.

Минимум учитывайте:
- обработку duplicate message/event;
- reconnect behavior;
- out-of-order events;
- delayed acknowledgements;
- unauthorized connection behavior;
- invalid payload behavior.

Даже если не все случаи пока автоматизированы, эти риски нужно учитывать и упоминать.

---

## Рекомендации по ручной проверке

Ручная проверка допустима как дополнение, а не замена, когда:
- flow сильно интерактивный;
- websocket behavior сложно быстро покрыть;
- infra dependencies делают автоматизацию непрактичной для текущей задачи.

При ручной проверке укажите:
- точный проверенный scenario;
- точный observed result;
- что осталось непроверенным.

Не пишите "manually tested" без деталей.

---

## Правила качества assertions

Хорошие тесты:
- проверяют поведение, а не внутренние детали;
- падают на реальных regressions;
- легко читаются;
- используют понятный setup и naming.

Плохие тесты:
- зеркалят реализацию построчно;
- чрезмерно используют mocks;
- проверяют нестабильные детали;
- создают ложную уверенность.

---

## Ожидания по регрессиям

При исправлении бага:
- добавьте или обновите тест, который поймал бы этот баг снова, если в этой зоне уже есть тесты или добавить тест практично.

При изменении поведения:
- обновите затронутые тесты вместо того, чтобы оставлять устаревшие expectations.

Не оставляйте behavior-changing diff без корректировки валидации.

---

## Минимальный стандарт завершения

Нетривиальная задача не завершена, если:
- измененное поведение не было валидировано подходящим способом;
- релевантные automated checks не были запущены, хотя они доступны;
- результат не был проверен на очевидные regressions;
- итоговый ответ не говорит, что было проверено и что нет.

"Code written" недостаточно.
"Looks correct" недостаточно.

---

## Ожидания к итоговому ответу после тестирования

В итоговом summary задачи укажите:
- какие tests/checks были запущены;
- прошли ли они;
- какие checks нельзя было запустить;
- оставшиеся risk areas;
- рекомендуемую follow-up validation, если нужна.

Будьте честны и конкретны.
